# Execution-bound static pipeline provenance

Implementation is opt-in with `PIPELINE_PROVENANCE_ENABLED=true`; webhook dispatch also requires `PIPELINE_PROVENANCE_RECOVERY_ENABLED=true` and migration 018 readiness. It is OFF by default, requires migration 017, and does not enable real Terraform planning, apply, AWS deployment or Active DAST. No production environment was changed during implementation. Existing legacy/manual pipelines remain unchanged while this flag is off; they cannot become deployment eligible. With the flag on, executions without a source revision fail closed rather than using a branch HEAD. Manual/commissioning source admission is not implemented by this webhook-only feature.

## Webhook admission

The existing raw-body repository-specific HMAC check remains first. The enabled admission path requires the GitHub numeric repository ID, `refs/heads/...`, a nondeleted 40-character nonzero push `after` SHA and a UUID delivery ID. It rechecks current project owner/repository under a database lock. An explicitly approved private deployment policy selects the static profile and approved branch; ordinary pipeline pushes use the signed repository's default branch and never receive static deployment approval merely from that assertion.

Source revision, TRIGGERED execution and delivery receipt commit together. Delivery UUID and payload SHA-256 reject conflicting/cross-project replay. Project/repository/branch/commit uniqueness and a project transaction advisory lock deduplicate both concurrent deliveries and the same commit under another delivery ID. An already-bound commit with a different approval requires explicit reconciliation. Ping/non-push handling and signature rejection remain unchanged. Commit succeeds before invoking the orchestrator. The bounded pre-start dispatcher in [provenance-webhook-recovery.md](provenance-webhook-recovery.md) now recovers committed TRIGGERED work when separately activated with migration 018. Already-started scans are never automatically retried.

Every scanner and staging checkout fetches and detaches the exact bound SHA after validating its origin repository. Branch movement cannot silently change execution source; missing objects or mismatches stop execution. New Git subprocesses have finite deadlines, bounded output and process-group termination. No credentials appear in command failures.

## Artifact format and staging

The first supported profile is a repository-root static site with `index.html`, plain HTML/CSS/JavaScript and allowed static assets. Package/build/server manifests, other executable formats, executable Git modes, submodules, symlinks, hidden content and unsafe paths are rejected. Known credential/configuration/documentation files are excluded; known embedded credential patterns fail validation. This is a conservative allowlist and pattern check, not proof that arbitrary source contains no unknown secret: approved source/webroot review and the security stages remain necessary.

Git tree/blob contents at the bound revision are compared with the checkout. Sorted path/size/content-SHA/base64 records and the source commit form deterministic `artifact.json`. Limits: 2,000 files, 25 MiB total content, 5 MiB per file, 240-character paths. No archive extraction or repository build scripts are executed to create it. Private owner-owned non-symlink storage is required; execution directory 0500, file 0400, atomic rename after fsync. Repeated creation verifies the existing artifact instead of replacing it. File and manifest integrity are rechecked on reuse, staging materialization and eligibility. Publishing must use this same verified reference; no AWS publisher exists yet.

Static staging discards the repository build context and materializes only the immutable site's files. It generates the existing pinned nginx runtime Dockerfile, removes inherited public content and installs a file-checksum manifest. Checks run during image build and container startup. Existing image vulnerability scanning, immutable built/running image-ID verification, Kubernetes security controls and readiness checks remain mandatory. No Minikube build/deployment was executed during implementation.

## Attestations and eligibility

Immutable database attestations are append-only per stage record (so genuine new scan attempts do not overwrite earlier evidence) and bind stage record ID, project/execution, commit, artifact, normalized snapshot, stage tool identity/version, completion time, native-result hash and persisted detail digest. Eligibility checks current parent/detail hashes rather than trusting stored PASS flags. JSON hashing is canonical across PostgreSQL JSONB key ordering.

SAST checks fresh scanner task output, CE task identity/success, latest analysis ID and revision before/after issue collection. It binds the quality gate to that analysis ID, verifies indexed coverage, records actual SonarQube/scanner versions, and derives security-only counts/review status from persisted classified issues. A SonarQube edition/API that cannot expose the expected analysis revision remains blocked; runtime compatibility is not claimed from fixtures.

Dependency records actual Trivy version, parsed vulnerability/SBOM result hash, valid persisted CycloneDX BOM and explicit manifest/package coverage. IaC requires a real parsed report. Unknown severity rows block attestation. Their native summary counts must match persistence. Passive DAST requires a digest-pinned ZAP image, persisted completed BASELINE findings and the exact execution staging URL. Deploy binds actual built/running image identity to the immutable static context. Child evidence changes, missing/skipped stages, wrong targets, stale approvals and artifact/source mismatches cannot qualify. Native stdout/raw report retention is not expanded here; hashes and execution-linked database details are retained, with existing report-retention limitations unchanged.

A new denial invalidates pending/claimed outbox events for that execution. Artifact/source integrity exceptions also attempt ownership-scoped durable invalidation after rollback. Consumer-side revalidation remains mandatory if durable storage is unavailable. There is no AWS consumer. An existing outbox event can never authorize an operation solely because it was once eligible.

## Migration and tests

Migration 017 remains unapplied to live PostgreSQL. Its source revisions, receipts, artifact bindings, attestations and decisions are append-only with composite project/execution foreign keys and uniqueness constraints. `node backend/scripts/test-deployment-provenance-postgres.js` creates a private PostgreSQL 15 cluster with TCP disabled and a private Unix socket; it never loads backend/.env or connects to the live database. It tests whole-migration rollback, actual concurrent delivery/decision inserts, claim leases, recovery, replay and preserved fixture sentinels. It stops/removes its cluster and retains private result/log evidence. These are synthetic fixture records, not a restore of production data.

Next: review the expanded migration 017, perform the established backup/isolated-restore procedure and separately authorize live application. Then approve a private static-site policy for an eligible unprotected project and authorize loading the provenance flag. A separately authorized real pipeline is still required to measure Sonar/scanner/staging integration; no runtime readiness is inferred from local fixtures. AWS execution, both real-planning gates and Active DAST remain disabled.
